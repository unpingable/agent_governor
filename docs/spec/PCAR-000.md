# PCAR-000: Proof-Carrying Agent Runtime
## Runtime Constitution for Evidence-Bound LLM Actuation

## 1. Abstract

This document defines the **Proof-Carrying Agent Runtime (PCAR)** protocol family: a runtime constitution for LLM-based systems in which language has no direct execution authority.

PCAR separates:
- **proposal** (model-generated language and plans),
- **verification** (proof objects bound to world state and time),
- **control** (constraint/regime decisions),
- **provenance** (receipts), and
- **actuation** (execution of proof-carrying contracts).

The goal is not to eliminate model error. The goal is to ensure that model error cannot directly produce unaudited state change.

---

## 2. Scope

PCAR specifies runtime contracts for:
- typed model claims,
- machine-checkable proof objects,
- constraint and regime decisions,
- receipt emission and chaining,
- proof-carrying actuation, and
- replayable incident analysis.

PCAR does **not** specify:
- model architecture or training methods,
- UI/UX interaction design,
- policy content (only policy interfaces),
- business logic for any specific domain.

---

## 3. Design Principles

### 3.1 No Linguistic Authority
Free text may propose, explain, or request. It may not authorize consequential action.

### 3.2 Proof-Carrying Action
Consequential actions require machine-checkable proof objects.

### 3.3 Temporal Binding
Proof validity is bounded by explicit freshness semantics (`Δt` windows).

### 3.4 Receipted Consequence
All consequential runtime decisions and executions emit receipts.

### 3.5 Replayability
A governed run MUST preserve enough structure to support deterministic or differential replay.

## 5. Terminology

### 5.1 Claim Envelope
A typed, structured representation of a model-emitted proposition or request.

### 5.2 Proof Object
A machine-checkable evidence artifact generated by a verifier and bound to a concrete state and time.

### 5.3 Constraint Decision
A deterministic control-law output indicating whether a requested action is allowed, denied, deferred, or requires re-verification.

### 5.4 Regime
A derived runtime operating mode computed from evidence quality, contradiction signals, drift, and policy thresholds.

### 5.5 Receipt
A canonical, hashable record of a consequential decision or execution event.

### 5.6 Actuator
A runtime component that executes structured action contracts only when proof and constraints are valid.

### 5.7 `Δt`
The elapsed validity interval between proof observation and attempted use. PCAR treats `Δt` as a first-class governance variable.

### 5.8 Constitutional (disambiguation)
PCAR uses "constitutional" in the runtime/governance sense: separation of powers, enumerated authority, execution constraints. This is distinct from "Constitutional AI" (Anthropic), which refers to training-time behavioral shaping via self-critique during RLHF. Constitutional AI governs model behavior. PCAR governs executable authority. They are complementary, not competing — a Constitutional AI model can run inside a PCAR runtime.

---

## 6. Protocol Family Overview

PCAR is a protocol family composed of tiered contracts:

- **PCAR-A** — Typed Claim Envelope
- **PCAR-B** — Proof Object and Verifier Contract
- **PCAR-C** — Constraint / Regime Decision Contract
- **PCAR-D** — Receipt Canonicalization and Provenance Contract
- **PCAR-E** — Actuator Contract
- **PCAR-R** — Replay Artifact Contract (recommended)

PCAR-000 defines the family model and cross-tier invariants. Companion documents define field-level schemas and error semantics.

---

## 7. Architecture Model

### 7.1 Role Separation

#### Proposer (Model Runtime)
Generates claims, plans, and action requests.
**No direct authority.**

#### Verifier Mesh
Transforms tool outputs and state observations into proof objects.
**No direct actuation.**

#### Constraint Engine
Evaluates typed claims + proofs + policy into deterministic decisions.
**No free-text authority path.**

#### Receipt Kernel
Emits canonical receipts for all consequential events.
**No silent consequence.**

#### Actuator
Executes structured action contracts if and only if constraints and proof requirements are satisfied.
**Dumb on purpose.**

### 7.2 Trust Boundary

PCAR places the trust boundary at the runtime execution interface, not at the model's self-report.

Model confidence is non-authoritative metadata.

---

## 8. Cross-Tier Invariants

The following invariants apply to all PCAR-conformant systems:

### 8.1 NLAI Invariant
A system MUST NOT treat natural-language text as sufficient authorization for consequential state change.

### 8.2 Proof Requirement Invariant
A consequential action MUST reference all required proof objects defined by policy and action type.

### 8.3 State Binding Invariant
Proof objects used in decision-making MUST bind to an immutable or content-addressed state reference (e.g., commit hash, file digest, snapshot ID, environment fingerprint).

### 8.4 Freshness Invariant
A proof object MUST include explicit freshness semantics. Expired proof MUST NOT be reused without re-verification.

### 8.5 Receipt Invariant
Constraint decisions and actuator outcomes MUST emit canonical receipts before or atomically with consequence.

### 8.6 Determinism Invariant
Given identical claim envelopes, proof objects, policy version, and runtime inputs, a constraint engine MUST produce the same constraint decision.

### 8.7 Replay Invariant
A governed run MUST preserve sufficient artifacts to reconstruct the decision path.

---

## 9. Processing Model (End-to-End)

A PCAR-conformant runtime follows this sequence:

### 9.1 Claim Emission
The proposer emits one or more Claim Envelopes (PCAR-A), optionally including a `REQUESTED_ACTION`.

### 9.2 Verification
Verifiers inspect claims and/or requested actions and emit Proof Objects (PCAR-B) bound to:
- evidence digests,
- state references,
- observation timestamps,
- freshness validity.

### 9.3 Constraint Evaluation
The constraint engine evaluates:
- Claim Envelopes,
- Proof Objects,
- Policy Pack,
- Runtime State,
- `Δt` / coherence signals,

and emits a Constraint Decision (PCAR-C).

### 9.4 Decision Receipt
The receipt kernel emits a decision receipt (PCAR-D) recording the inputs and outcome.

### 9.5 Actuation
If allowed, the actuator validates the Action Contract (PCAR-E), executes the action, and emits an execution receipt.

### 9.6 Replay Persistence
All relevant artifacts are persisted or content-addressed for replay (PCAR-R).

## 10. Tier Summaries (Normative)

### 10.1 PCAR-A (Typed Claims)
PCAR-A defines Claim Envelope serialization, claim types, and parsing/normalization rules.

At minimum, implementations MUST support these claim types:
- `OBSERVED`
- `INFERRED`
- `ASSUMED`
- `PLANNED`
- `REQUESTED_ACTION`
- `UNVERIFIED`
- `POLICY_INTERPRETATION`

Untyped consequential language MUST be downgraded to `UNVERIFIED`.

### 10.2 PCAR-B (Proof Objects)
PCAR-B defines proof object schemas, verifier identities, evidence hashing, state binding, and freshness semantics.

Proof objects MUST:
- hash raw evidence payloads,
- bind to state,
- include observation time,
- include validity semantics,
- include verifier identity/version,
- record `PASS`, `FAIL`, or `INCONCLUSIVE`.

### 10.3 PCAR-C (Constraint / Regime)
PCAR-C defines deterministic control-law evaluation and regime derivation.

Constraint decisions MUST return one of:
- `ALLOW`
- `DENY`
- `DEFER`
- `REVERIFY`
- `ESCALATE`

Regime labels are implementation-defined but MUST be derivable from recorded signals and policy thresholds.

### 10.4 PCAR-D (Receipts)
PCAR-D defines canonical receipt serialization and hashing.

Receipts MUST:
- reference all relevant proof IDs,
- bind to policy and constraint hashes,
- record actor and event type,
- include timestamp,
- be canonicalized prior to hashing.

Human overrides MUST emit receipts.

### 10.5 PCAR-E (Actuator)
PCAR-E defines proof-carrying action contracts and execution validation rules.

Actuators MUST:
- reject free-text authority paths,
- reject expired contracts,
- enforce scope mechanically,
- emit post-execution receipts.

### 10.6 PCAR-R (Replay)
PCAR-R defines replay artifact format and compatibility.

Replay artifacts SHOULD support:
- exact replay,
- policy-diff replay,
- verifier-diff replay,
- counterfactual replay.

## 11. State Machine (Conceptual)

PCAR runtimes MUST expose a deterministic state machine for action requests.

### 11.1 Required States
- `PROPOSED`
- `VERIFICATION_PENDING`
- `VERIFIED_PARTIAL`
- `DECIDED`
- `EXECUTION_PENDING`
- `EXECUTED`
- `DENIED`
- `DEFERRED`
- `EXPIRED`

### 11.2 Required Transitions
- `PROPOSED -> VERIFICATION_PENDING`
- `VERIFICATION_PENDING -> VERIFIED_PARTIAL`
- `VERIFIED_PARTIAL -> DECIDED`
- `DECIDED -> EXECUTION_PENDING` (if `ALLOW`)
- `EXECUTION_PENDING -> EXECUTED`
- `DECIDED -> DENIED`
- `DECIDED -> DEFERRED`
- `* -> EXPIRED` (if freshness invalidates pending artifacts)

Implementations MAY add internal states, but MUST preserve equivalent observable semantics.

## 12. Error Model

PCAR companion specs MUST define machine-readable error codes.

The following error classes are REQUIRED:

- `PCAR_A_*` — claim parsing / typing errors
- `PCAR_B_*` — proof generation / verifier errors
- `PCAR_C_*` — policy/constraint evaluation errors
- `PCAR_D_*` — receipt serialization / hashing errors
- `PCAR_E_*` — actuator contract / execution errors
- `PCAR_R_*` — replay artifact / compatibility errors

### 12.1 Error Handling Rules
- Errors MUST be machine-readable.
- Consequential failures MUST emit receipts if any decision or execution step was attempted.
- `INCONCLUSIVE` proof results MUST NOT be silently upgraded to `PASS`.

---

## 13. Canonicalization Requirements

PCAR-D companion spec MUST define canonical serialization for:
- Claim Envelopes (if hashed)
- Proof Objects
- Constraint Decisions
- Receipts
- Action Contracts

Canonicalization MUST eliminate ambiguity due to:
- field ordering,
- whitespace,
- float formatting,
- timestamp precision variance,
- optional/null field normalization.

If canonicalization is undefined, receipt hashing is non-portable and non-comparable.

---

## 14. Policy Interface

PCAR does not prescribe policy content, but it defines policy interface requirements.

A Policy Pack MUST be:
- versioned,
- hashable,
- loadable by the constraint engine,
- referenceable in receipts.

Policy evaluation inputs SHOULD include:
- action type,
- target scope,
- proof set,
- freshness status,
- regime signals,
- prior failure counters (optional),
- human override context (optional).

## 15. Security Considerations

### 15.1 Prompt Injection
PCAR mitigates prompt injection by removing natural language as an authority path. However, prompt injection may still influence proposal content and verifier targeting. Implementations MUST scope verifier permissions and actuator capabilities.

### 15.2 Proof Forgery / Substitution
Proof objects MUST bind to evidence digests and state references. Mutable references without content digests are insufficient.

### 15.3 Replay / Nonce Reuse
Actuator contracts SHOULD include nonces or idempotency keys. Expired or replayed contracts MUST be rejected.

### 15.4 Time Skew
Freshness semantics depend on time integrity. Implementations SHOULD use trusted clocks or signed time attestations in high-assurance contexts.

### 15.5 Verifier Compromise
Verifier identity/version MUST be recorded in proof objects and receipts. Policy SHOULD support verifier allowlists and version pinning.

### 15.6 Human Override Abuse
Human overrides are necessary but hazardous. Overrides MUST be explicit, scoped, and receipted.

---

## 16. Privacy Considerations

Receipts and proof payloads may contain sensitive data. Implementations SHOULD support:
- payload redaction with digest preservation,
- encrypted evidence stores,
- scoped retention policies,
- role-based access to replay artifacts.

Privacy controls MUST NOT break proof digest integrity or replay semantics without explicit indication.

---

## 17. Conformance

An implementation is **PCAR-family conformant** if it:

1. Enforces the cross-tier invariants in Section 8.
2. Implements PCAR-A through PCAR-E contracts (PCAR-R RECOMMENDED).
3. Emits canonical receipts for all consequential decisions and executions.
4. Enforces proof-carrying action at the actuator boundary.

Implementations MAY be additionally labeled:
- **PCAR-R Conformant** (replay support),
- **PCAR-HA Conformant** (high-assurance profiles; future profile spec).

## 20. Example Non-Normative Flow (Informative)

A model emits:
- `PLANNED`: run tests
- `REQUESTED_ACTION`: execute `pytest` in repository scope

Verifier emits:
- `STATE_SNAPSHOT` for repo commit
- `TOOL_RESULT` for `pytest` execution
- `TEST_RESULT` parsed from output
- `FRESHNESS_CHECK` on snapshot age

Constraint engine evaluates proofs and returns `ALLOW` for a subsequent file write request, under current regime.

Receipt kernel emits decision receipt, actuator executes the write, and emits execution receipt.

All artifacts are stored for replay.
