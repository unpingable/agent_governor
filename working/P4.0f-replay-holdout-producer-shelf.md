## Design lean (operator, 2026-06-14)
**Thin receipting adapter over the existing C1 `REPLAY_HARNESS`, not a standalone
mini-producer** — unless the harness is too entangled to wrap. Reason: Checkpoint 1
ratified replay/holdout as the *second witness*; a separate producer risks inventing
sibling replay semantics. The producer ATTESTS an existing run; it does not invent
replay logic, selection semantics, or promotion judgment.

## Fence

Must BIND:
- trial_id / candidate id
- comparator baseline id
- corpus / holdout-set hash (frozen, recorded before evaluation)
- harness identity / version
- observed run result / child exit
- non-regression verdict

Must REFUSE:
- missing comparator baseline
- missing / floating corpus hash
- failed harness run
- stale or mismatched harness identity
- verdict not bound to trial_id
- replay pass not walkable to recorded run evidence

Must NOT:
- mint ControlBaseline
- count live observations
- decide PromotionEligible by itself
- import `convergence_tuning`
- mutate baseline / config

## Carry the P4.0e discipline forward
Same trust boundary: **producer-derived ≠ producer-trusted.** Whatever the producer
records, the load/consume path re-validates (corpus-hash match, harness identity,
trial binding, verdict-walkable-to-run-evidence) rather than trusting the stored
verdict. Hash the inputs, treat the stored verdict as an accusation against them.

## After P4.0f
`OperatorBasisReceipt` is the **last** producer — and the obnoxious one: it must
capture "operator present / basis reviewed" WITHOUT turning operator mood into
evidence. Design problem deferred ("Tuesday").

Only after all three producers exist could the pipeline return `eligible` on *real*
evidence — at which point **P4.0b** (mint the baseline via the supersession ceremony)
becomes live: HIGH / operator-present, Checkpoint-3-gated. Do not cross that line cold.
